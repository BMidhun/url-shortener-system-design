# LOAD TESTING USING k6

This guide shows how the load test has been performed for this application. Follow this guide by each section sequentially to understand the whole setup.

## Prerequisites

- Make sure your database is running
- You will have to run the server application connected to your local postgres database.
- Truncate the existing table with this sql command (optional)

```sql
TRUNCATE TABLE "shortURLTableSchema"."shortURLTable" RESTART IDENTITY CASCADE;
```

## Data Dumping

Prior to perform the load test, make sure we have enough large amount of data for the test.
File data-dump.js will create 500 entries in the DB by calling the POST request of the server application.

```bash
    > node data-dump.js
```

## Creating sample-data.json file

Create a sample-data.json file that will contain the test data of _short_code_ used for testing the GET request /:shorten

Run the command aganist your DB

```sql
> SELECT json_agg(
    json_build_object(
        'short_code', short_code
    )
  )
  AS json_output
  FROM "shortURLTableSchema"."shortURLTable";
```

The above command will create an array of object like this [{short_code: "ASdasdasd"}]

## Installing K6 (Load testing tool)

Install k6 on your local machine

- macOS: brew install k6
- Windows (Chocolatey): choco install k6
- Linux (Ubuntu/Debian): sudo apt-get install k6

## Running K6 Script

While K6 script may look like a JS code, infact it is not a native nodejs code as k6 does not run directly inside a Node.js engine; it is written in Go and uses a custom JavaScript runtime.

Before running k6 script make sure you are running a scaled up version of your application using the following command.

```cmd
    >docker compose --env-file .env.loadtest up --build --scale express-app=5 -d
```

_In the .env.loadtest file we set the NODE_ENV=loadtest. This will make sure the rating limiting middlewares are disabled_

```cmd
    > k6 run load-test.js
```

## Analyzing the Load Test Results

This report breaks down the performance metrics generated by **Grafana k6** during the 30-second load test simulating 50 concurrent users on your URL shortener.

### 1. Executive Summary

Overall, the system handled the load exceptionally well under pressure. The server processed **14,344 total requests** over 30 seconds with an amazing success rate of **99.89%**.

### 2. Test Configuration (`Scenarios`)

- **Execution Mode**: Run locally (`execution: local`) on your machine.
- **Traffic Load**: Maintained a steady baseline of **50 Virtual Users (VUs)** looping through requests continuously.
- **Test Duration**: Run for **30 seconds** with an additional 30-second graceful window to allow in-flight requests to safely finish processing.

### 3. Verification & Errors (`Checks`)

The test executed **14,344 health assertions (checks)** to verify if your server was sending back valid HTTP status codes:

- **Read Traffic (GET Requests)**: **100% Success Rate**. Every single attempt to look up or resolve a shortened URL successfully returned an expected status code (`301`, `302`, or `404`).
- **Write Traffic (POST Requests)**: **98.92% Success Rate** (1,390 passed, 15 failed). Out of 1,405 link creation requests, exactly **15 requests failed**.
- **Total Failure Rate**: Only **0.10%** of all network operations failed across the entire lifecycle of the test.

### 4. HTTP Performance & Latency

Your NGINX load balancer and scaled Express backend setup delivered incredibly fast response times:

- **Average Response Time (`avg`)**: **4.01 ms**. The system responds almost instantaneously under standard conditions.
- **Median Response Time (`med`)**: **2.59 ms**. Half of all incoming requests were resolved in under 2.6 milliseconds.
- **Spike Latency (`max`)**: **276.2 ms**. The slowest response took roughly a quarter of a second, which typically happens during initial database handshake connections or container warmups.
- **Percentiles (`p90` / `p95`)**:
  - 90% of your users experienced response times under **6.91 ms**.
  - 95% of your users experienced response times under **9.91 ms**.

### 5. Network Throughput

- **Request Volume**: The application successfully sustained a massive traffic speed of **476 requests per second (req/s)**.
- **Data Transferred**: The network moved **16 MB of data incoming** (545 kB/s download) and **1.5 MB of data outgoing** (51 kB/s upload).

### 💡 Core Takeaway & Next Steps

Your architecture is highly performant! Processing nearly 500 requests per second with a median latency of under 3 milliseconds is excellent for a containerized application stack.

The only point of concern is the **15 failed POST requests**. This minute bottleneck is likely caused by database connection pooling limits (PostgreSQL running out of available client slots) or Redis locking during rapid concurrent inserts.

## Understanding the Code

This script is a load-testing script built for **Grafana k6**. It simulates heavy user traffic to test how well your URL shortener system handles real-world requests.

Here is exactly how the script works from top to bottom:

### 1. Efficient Data Loading (`Init Context`)

```javascript
const data = new SharedArray("sample data", function () {
  return JSON.parse(open("./sample-data.json"));
});
```

- **Memory Management**: Loading files normally in k6 copies the data for _every single virtual user_, which quickly crashes your computer's memory. `SharedArray` safely loads the `sample-data.json` file into memory exactly **once** and shares it across all users.
- **The `open()` function**: This is a built-in k6 function used to read files. It will throw an error if you try to run this script using Node.js (`node script.js`). It must be executed via the k6 CLI.

### 2. Test Configuration (`options`)

```javascript
export const options = {
  vus: 50,
  duration: "30s",
  insecureSkipTLSVerify: true,
};
```

- **`vus: 50`**: Configures the test to run with **50 Virtual Users** concurrently mimicking human actions.
- **`duration: "30s"`**: The load test will run continuously for exactly 30 seconds.
- **`insecureSkipTLSVerify: true`**: Tells k6 to ignore self-signed SSL/TLS certificate errors. This is required because your local NGINX load balancer uses local `mkcert` certificates.

### 3. Simulating Real User Traffic (`actionChance`)

Inside the `default` function, the script calculates a dynamic threshold using `Math.random() * 100`. This splits your user traffic into two realistic behaviors:

#### 🟢 The 10% Write Traffic (POST Request)

- **What it does**: Simulates users creating new shortened URLs.
- **Payload**: Generates a randomized URL payload (e.g., `https://example.com`) to avoid hitting database caching layers.
- **Validation**: The `check()` block confirms that your Express backend successfully saves the data and returns a successful status code (`200` or `201`).

#### 🔵 The 90% Read Traffic (GET Request)

- **What it does**: Simulates the heavy load of people clicking on shortened links to be redirected.
- **Data Selection**: Randomly grabs a pre-existing short code from your loaded `sample-data.json` file.
- **Redirect Handling**: `redirects: 0` tells k6 **not** to follow the redirect location. It just measures if your NGINX/Express setup successfully issues the HTTP redirect (`301`/`302`) or a clean `404` for missing codes.

### 4. Pacing Control (`sleep`)

```javascript
sleep(0.1);
```

- **The Pause**: Every single Virtual User pauses for exactly `0.1` seconds (100 milliseconds) at the end of their loop before sending another request. This stops your testing machine from overwhelming itself and mimics realistic human clicking speeds.
